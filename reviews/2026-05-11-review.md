# Juno Financial Dashboard — Review

**Date:** 2026-05-11
**Reviewer:** senior reviewer agent
**Scope:** full pass against current `main` (v10/v11/v12 features described in README, MIGRATION, ASSISTANT_SETUP). A live-site addendum was added after the initial pass — see §6.
**Method:** read-only inspection of `public/`, `audit/`, top-level docs, `render.yaml`, `serve.py`. Live site loaded at https://juno-dashboard.onrender.com for the §6 addendum.

---

## 1. Summary

The dashboard is a competent financial replacement for the Excel workbook — the engine is pure, the KPI surface is broad, and a `Match Excel` reconciliation mode hits ~$1.6k variance on $72M of sales. That is real, useful progress. But the platform is now being sold as the operational system of record (per MIGRATION.md it is meant to retire the Excel by ~2026-05-18) and the supporting infrastructure is nowhere near that bar. **The single most important issue is that the entire server-side security model — Supabase RLS policies, the `get_state_for_current_user` redaction RPC, and the assistant Edge Function source — is not in this repo.** Everything that protects financials from viewer-class users, prevents prompt injection, redacts data for the LLM, and gates writes to `financial_state` is invisible to review. Until those artifacts are committed, no claim about role-based access or LLM safety can be verified, and migration off the Excel should not happen.

Second: the "multi-user editor" feature is implemented with a known-broken concurrency model (`saveFinancialState` reads version then writes without compare-and-set), so two editors overwriting each other will go undetected. This is the kind of silent data loss that destroys trust in a system of record.

Third: while domain fit on the *finance* side is strong (lifecycle stages, waterfall, NOL, market multipliers, tornado, Monte Carlo), this is still a financial model with a login, not an "ops engine" for a residential developer in the sense the reviewer brief described. There is no GMP/change-order/RFI/permit/inspection capture, no marketing spend, no contingency tracking — none of the things a project manager touches between "land control" and "sold."

Do not retire the Excel until at least items 1–4 in **Critical issues** below are resolved.

## 2. Critical issues

### C1. The Supabase server-side code is not in the repo

`supabase.js` calls `rpc("get_state_for_current_user")`, reads/writes `financial_state`, `state_history`, `activity_log`, `llm_query_log`, `llm_suggestions`, `user_profiles`, `llm_rate_limit`, and invokes the `assistant` Edge Function. None of that is committed. There are no migration files, no `supabase/` directory, no Edge Function source, no RLS policies. ASSISTANT_SETUP.md and MIGRATION.md describe what should exist but those are docs, not artifacts.

This means:
- The RLS that supposedly prevents a `viewer_basic` from reading unredacted `financial_state` cannot be verified.
- The role lookup that the assistant Edge Function uses to decide redaction cannot be verified.
- The system prompt — including its anti-prompt-injection rules — cannot be audited.
- The RPC redaction logic (which fields are stripped for `viewer_basic`) cannot be checked against the client's expectations.
- A future migration that accidentally widens RLS or breaks the RPC has no diff to review.

**Action:** commit `supabase/migrations/*.sql`, `supabase/functions/assistant/index.ts` (or wherever it lives), and the system prompt as a versioned file before the Excel is archived. This is the gate.

### C2. Optimistic concurrency is not implemented; two editors silently overwrite each other

`saveFinancialState` (supabase.js:153) does:

```js
const current = await fetchFinancialState();
const newVersion = (current?.version ?? 0) + 1;
const { data, error } = await supabase
  .from("financial_state")
  .update({ state, version: newVersion, ... })
  .eq("id", 1)
  ...
```

There is no `.eq("version", current.version)` on the update. If user A and user B both load version 5, both save 2 seconds later, they both write version 6 and one set of edits is lost with no error and no warning. Given autosave fires every 2s on any edit (config.js:11), this is a near-certainty if two editors are active concurrently.

**Patch:**
```js
const expectedVersion = current?.version ?? 0;
const { data, error } = await supabase
  .from("financial_state")
  .update({ state, version: expectedVersion + 1, updated_by: user.id, updated_at: new Date().toISOString() })
  .eq("id", 1)
  .eq("version", expectedVersion)        // CAS guard
  .select("state, version, updated_at, updated_by")
  .single();
if (error?.code === "PGRST116" || !data) {
  throw new Error("State was changed by someone else. Please refresh.");
}
```

This still needs the UI to handle the surfaced error gracefully (prompt-to-refresh rather than red error toast in an autosave loop). Without it, the multi-user pitch in MIGRATION.md is a promise the system does not keep.

### C3. `fetchFinancialState` falls back to a direct read if the redaction RPC errors

supabase.js:142–151:

```js
const { data, error } = await supabase.rpc("get_state_for_current_user");
if (error) {
  console.warn("fetchFinancialState (rpc) failed:", error.message);
  // Fallback: try direct read (will fail for viewer_basic but work for others)
  const direct = await supabase.from("financial_state").select(...).eq("id", 1).maybeSingle();
  return direct.data || null;
}
```

The fallback assumes RLS on `financial_state` correctly forbids `viewer_basic` from reading the raw row. If that RLS policy is ever loosened (e.g. dropping `(role != 'viewer_basic')` predicate during a migration), or if the redaction RPC is dropped/renamed, every existing `viewer_basic` user silently starts getting the full, unredacted state. There is no defense-in-depth: the redaction RPC is the only safeguard, and the fallback explicitly bypasses it.

**Action:** if the RPC errors, refuse to load state for any user. Do not fall back. A failed RPC should be a hard error, not "try the next door."

### C4. `viewer_basic` redaction only works if the user stays on the views the UI hides

The financial-view guard is only `FINANCIAL_VIEWS = {"cashflow", "waterfall", "scenario", "sensitivity", "risk", "settings"}` (ui.js:251). `projects` and `project_detail` are **not** in that set. `renderProjectDetail` (ui.js:566) freely reads `p.land_cost_usd`, `p.build_cost_per_sqft`, `res.kpis.total_sales`, `res.kpis.gross_profit`, `res.kpis.moic`, `res.kpis.irr_annual`, `res.kpis.peak_equity` and dumps them straight into the DOM.

If the server RPC really is stripping those fields for `viewer_basic`, then `renderProjectDetail` would show "—" everywhere and the leak is null. **If the RPC is doing anything less than complete stripping** (e.g. zeroing financial fields, removing only top-level keys, missing `_excel_sale_price` or `actuals`), a `viewer_basic` can navigate to project_detail (via `setView("project_detail", ...)` from the console, or by reaching it before the FINANCIAL_VIEWS check fires — restricted-viewer redirect only catches the views in that set) and see the project's land cost, build budget, and profit. Cannot verify either way without the RPC source.

**Action:** (a) add `projects` and `project_detail` to FINANCIAL_VIEWS, or render them as a basic-stage-only view for `viewer_basic`; (b) commit the RPC and write a test that asserts the redacted blob is missing every financial field on every project; (c) keep #C3 — make the RPC the only path.

### C5. No server-side rate limit or cost cap on the assistant

ASSISTANT_SETUP.md:54 — "Per-user daily quota: unlimited. The `llm_rate_limit` table still tracks daily query count + cost per user for telemetry, but the Edge Function does not enforce a cap." A stolen JWT or a curious editor can run up unbounded Anthropic spend. The published cost estimate of "$5–30/month, heavy: $50–150" assumes well-behaved humans; it ignores adversarial misuse and runaway client loops. Anthropic's billing is post-paid; the first warning is the invoice.

The fix is the 5-line addition described in the doc itself (re-introduce `DAILY_QUERY_LIMIT`), but layered: a per-user daily query cap, a per-user daily $ cap, **and** an account-wide daily $ cap with a circuit breaker that returns "service temporarily unavailable" when tripped. Page the super_admin via email/webhook when the account cap is hit.

### C6. Validation scripts in `audit/` no longer run

`audit/07_validate.mjs`, `10_validate_v3.mjs`, `16_compare_equity.mjs`, `17_match_excel.mjs`, `18_build_seed.mjs` all import `../data.js` and `../engine.js`. Those files now live at `public/data.js` and `public/engine.js`. Anyone running `node audit/17_match_excel.mjs` today gets `ERR_MODULE_NOT_FOUND`. The headline reconciliation numbers in PHASE_4_VALIDATION.md ("Total sales match within $1,594", "Profit pre-tax within 5.6%") cannot be regenerated without manually fixing import paths.

**Trivial fix.** Update the imports to `../public/data.js` and `../public/engine.js`. But until that's done, the validation claims are unverifiable and the "Match Excel mode" sales pitch in MIGRATION.md step 2 is built on a number nobody on the team can reproduce.

### C7. Single-row JSONB state defeats most of the protections that get advertised

All globals, all projects, all scenarios, the rolling audit log, and the UI cursor live in one row of `financial_state` (id=1) as a JSONB blob (see seed.sql). Consequences:

- **Field-level RLS is impossible.** You cannot say "viewer_basic can read projects.name but not projects.land_cost_usd" in Postgres — it's one column. The only redaction path is the RPC, which is what makes C1/C3/C4 so load-bearing.
- **`state_history` doubles in size every save.** Every keystroke flush stores a full snapshot of every project plus the in-state audit_log (which itself is up to 200 entries of JSON). The 50-row pruning policy will trip frequently; long-term storage growth is meaningful and the rollback semantics ("restore version 23") restore the audit log too, which is wrong (rollback should not erase the record of the rollback).
- **No foreign keys.** `activity_log.detail.project_id` is a string inside a JSONB column; project IDs can drift; no referential integrity.
- **Multi-editor merge is impossible without bespoke code.** Last-writer-wins, which is what C2 manifests.

This is a deliberate v1 simplification (per PHASE_2). Fine as a prototype. **Not** fine as a system of record. Plan the migration to proper tables (`projects`, `scenarios`, `globals`, `audit_events`) before the Excel is archived, not after.

## 3. Important but not urgent

### I1. `MOIC` and `peak_equity` are computed two different ways at project vs. portfolio level

- Per-project (engine.js:258): `MOIC = sum(equity_returned) / sum(equity_drawn)` from the per-project loan/equity engine.
- Portfolio (engine.js:511): `MOIC = totalEquityReturned / totalEquityCalled`, where `totalEquityCalled` is the sticky cumulative cash-flow-driven equity (Excel-style) and `totalEquityReturned = max(0, closing_cash[N-1])` (proxy for final liquidation).

These are different metrics. The portfolio version includes overheads and interest; the per-project version does not. The peak equity numbers diverge for the same reason — project-level peak uses `equity_balance` (decreases as residual returns), portfolio-level peak uses `cum_equity_called` (never decreases). A user looking at "Project p2 peak equity = $X" and "Portfolio peak equity = $Y" cannot reconcile by adding.

Either unify the methodology (preferred, since "portfolio MOIC" should be the sum-of-parts of project MOICs in a clean model), or label each metric explicitly in the UI: e.g. "Peak equity called (cumulative)" vs. "Peak equity outstanding (net)" and explain the difference once.

### I2. Portfolio IRR assumes full liquidation at horizon end

`equityCashFlowFromCalls` (engine.js:678) pushes `closing_cash[N-1]` into the last cell as the assumed final distribution. Right now Project 11's sale lands exactly in month 48 (the last grid month) so it happens to work. If anyone:

- adds a Project 12 with `start_date >= 2029-02`,
- pushes any existing project's start later, or
- extends `program_months` on a late-window project,

…then the assumption silently overstates IRR by treating in-flight cost basis as recoverable cash at horizon. Either lengthen the horizon dynamically based on the latest sale date, or assert at compute time and raise a visible warning when projects extend beyond the model window. The current behavior at engine.js:147 ("Project sits entirely outside the model window -> still emit a zero series") fails open.

### I3. Viewer banner says read-only, but every edit affordance is rendered

ui.js shows "+ Add project", "Delete", "Clone", "Exclude", per-project form inputs, and Settings inputs for users in the `viewer` role. The mutations call `addProject` / `updateProject` etc., which mutate in-memory state and call `save()`, which then silently bails for non-editors (state.js:194). The user sees their "edit" appear, the cloud-sync badge probably flicks to "pending → ?", and then the change vanishes on the next reload because it was never persisted.

Fix: gate the affordances. If `!canEdit()`, render inputs as `disabled`, hide Add/Delete/Clone buttons, and don't wire the form submit handlers. The current behavior trains users to distrust the UI.

### I4. Two parallel audit trails, with one bloating every save

Every mutation calls `logEvent(...)` (state.js:58), which (a) pushes to `state.audit_log` (max 200, in localStorage and shipped to Supabase as part of the JSONB state) **and** (b) fires `logActivityToServer(...)` (supabase.js:215) which writes to the `activity_log` table. Two writes per edit; the in-state version pollutes every `state_history` snapshot. The server `activity_log` is the proper audit trail. Remove the client-side ring buffer or stop persisting it in `financial_state`. The Activity view can read from the server table on demand.

### I5. Sold-project count in the portfolio header uses the legacy `status` field

ui.js:365: `state.projects.filter(p => p.status === "sold").length`. The new lifecycle stages (data.js:5 — eleven of them, including `stage: "sold"`) are what `isClosed()` in the engine actually checks. If a project's stage advances to `sold` without the legacy `status` also being updated to `"sold"`, the portfolio header undercounts. Use the same `isClosed(p)` check the engine uses.

### I6. `status` (4 values) and `stage` (11 values) both exist as primary lifecycle fields

`status`: pipeline / committed / in-build / sold (used in dropdowns, filters, badges).
`stage`: sourcing / land_control / entitlement / design / permitting / pre_construction / construction / pre_sales / under_contract / sold / archived.

Both are persisted on each project. New code uses `stage`; old code still uses `status`. They can diverge. A project can be `stage: "construction"` and `status: "pipeline"`. The UI shows both in different places (status in `renderProjectForm` line 738, stage in the badges). Pick one. Migrating to stage-only is the obvious call; leave `status` for backward compatibility on existing rows but stop reading it.

### I7. "Match Excel mode" 81% build realization is a reconciliation hack, not a forecast assumption

`build_cost_realization_pct: 1.0` by default, `0.81` in Match Excel mode. The 81% comes from Excel's monthly grid under-allocating relative to project totals — a defect of the Excel model, not a real-world cost spread. PHASE_4_VALIDATION is explicit about this, but the UI button "Match Excel mode" in Settings is one click, and once enabled, it silently changes every forecast going forward. A user trying to "see the Excel numbers" and forgetting to toggle it back will under-allocate $5.4M of construction cost on every subsequent decision. Either rename it to something like "Reconciliation snapshot" with a banner indicating "Forecasts are biased low while this is on", or make it a transient view rather than a state flag.

### I8. Domain coverage gaps that the reviewer brief explicitly flagged

The reviewer brief asked for KPIs typical of a residential developer: IRR, MOIC, profit margin %, cost per sqft (budget vs actual), schedule variance, sales velocity, absorption rate, days-on-market, sales price per sqft realized vs underwriting, contingency burn rate. Current state:

| KPI | Status |
|---|---|
| IRR (project + portfolio) | ✓ |
| Equity multiple / MOIC | ✓ but inconsistent definitions (I1) |
| Profit margin % | ✓ shown as `profit_margin_pct` and `Effective margin` |
| Cost per sqft (budget vs actual) | partial — per-project `actuals` exist; no portfolio-level aggregation |
| Schedule variance | missing — no actual-vs-forecast on start/sale dates |
| Sales velocity (units/month) | missing |
| Absorption rate | missing |
| Days-on-market | ✓ when listing_date and closing_date populated (default null) |
| Sale price realized vs underwriting | partial — captured per-project, no rollup |
| Contingency burn rate | missing — no contingency budget concept at all |
| **Cash-on-cash return** | missing (see Suggestions S1) |

A residential developer running ten sequential projects across four years would absolutely want schedule variance, contingency, and absorption on the portfolio screen. The fact that they're not there means the dashboard is "Excel + login," not "Excel + the things Excel was bad at."

### I9. Operational data captured is thin

Inputs at the project level: lifecycle stage, sqft, land cost, build psf, kingshaus psf, target margin, interest, LTC, soft costs (lump or 7-line breakdown), sale override, market, listing/under-contract/closing dates and prices, and 5-line actuals.

Not captured anywhere: GMP / GC contract amount, change orders (count or $), RFIs, permit application/issue dates, inspection milestones, contractor/sub list with status, marketing spend, lender name and covenants, draw schedule (the LTC% is treated as a single number, not a draw curve with conditions), inspector/architect/lawyer fees as separate line items beyond the soft-cost lump, investor cap table per project (only a global one exists), title issues, easements, environmental review, HOA dues, property tax during hold, insurance during hold.

This is fine if the project's scope is "replace the financial model"; it is not fine if it's "operational system of record." MIGRATION.md frames it as the latter. Decide which, and either ship the operational layer or stop selling it as such.

### I10. `serve.py` binds 127.0.0.1, but DEPLOY.md tells users how to flip it to 0.0.0.0

DEPLOY.md option 3 says: "For multi-user access on a LAN, change the bind address in `serve.py` from `127.0.0.1` to `0.0.0.0` and open the firewall on port 8765." This is a no-cache static server with zero auth (the Supabase auth runs in the browser). On 0.0.0.0, anyone on the LAN can hit it and get the bare `index.html`, which then negotiates with Supabase via the publishable key. Supabase auth still gates them out of `financial_state`, but the publishable key is now also handed to any LAN client. Fine in theory; in practice this guidance invites a sloppy production deploy. Either drop that instruction or add a paragraph about putting it behind nginx + basic auth.

### I11. `subscribeToStateChanges` is exported but never used

supabase.js:329. The realtime channel for cross-client updates exists in code but is never wired in `state.js` or `main.js`. So when User A saves, User B does not see the update until they reload. Combined with C2's concurrency hole, this means the multi-user story is "everyone refresh after every edit" — which nobody will do.

### I12. `escapeHtml` is correctly applied to assistant output, but only in the chat panel

ui.js:1635–1638 escapes user and assistant messages before injection — good. But `Suggestion` view (ui.js:1722–1731) also stringifies `original_message`, `llm_summary`, and `proposed_patch` through `escapeHtml`. Also good. What's NOT escaped: any field rendered via `\`${p.name}\`` etc. into template literals throughout the file. Project names, addresses, scenario names are inserted raw into the HTML. If an editor sets a project name to `<img src=x onerror=alert(1)>`, it executes the next time the projects list is rendered. The trust boundary here is "any editor is trusted" — fair for a small team, but worth flagging because the same UI is shown to viewers, so an editor with malicious intent can XSS a viewer. Not a critical issue because it's an insider attack on an internal tool, but it's the kind of thing that should be fixed before any external investor is given a viewer login (which is on the roadmap per MIGRATION.md step 3).

## 4. Suggestions

Ranked by how much they'd matter for the people actually using this.

### S1. Add cash-on-cash return per project and portfolio

This is the first metric a residential investor asks for and it's not a named KPI right now. Equity cash flows are already computed; this is a one-line addition: `cash_on_cash = annualized_equity_distributions / total_equity_in`. Surface it next to MOIC on Project Detail and Portfolio. Distinguish "unlevered yield on cost" from "leveraged cash-on-cash" — both are useful, and the dashboard already has the inputs for both.

### S2. Add schedule variance and contingency burn

Schedule variance: for each project past its forecast start, compute `actual_start - forecast_start` (months) and propagate to a forecast sale-date shift. Contingency: add a global `contingency_pct` (default 5–10%) applied to the build budget; track `contingency_used` as part of the existing actuals object. Surface "Contingency remaining" per project and as a portfolio aggregate. These are the operational metrics a residential developer most often *doesn't* track in Excel and therefore most benefits from in a real system.

### S3. Commit the missing infra (`supabase/migrations/*.sql`, `supabase/functions/assistant/*`)

Already discussed in C1. Listed here too because nothing else in the suggestion list matters if the security model can't be reviewed.

### S4. Replace single-row JSONB with proper tables for `projects` and `globals`

Already discussed in C7. Cost: several days of migration + RLS rewrite. Benefit: half the items on this review (C2, C3, C4, I4, I11) collapse into "RLS handles it."

### S5. Ship per-project change-order / RFI tracking before the next investor cycle

If the goal is "replace Excel for running development projects," the single feature that would most demonstrate operational maturity is change-order capture. Add `change_orders[]` per project with date, description, $ amount, approver, status. Roll it up into a "change order exposure" column on the portfolio table. It's a small data model addition with large credibility impact for any external viewer (investor, lender) looking at the dashboard.

## 6. Live-site addendum (production deploy is bricked)

Added after the initial pass at the master admin's request. I loaded https://juno-dashboard.onrender.com in a desktop browser at 1440×900 and 1568×751 viewports.

### Headline: C0 — the production site never gets past "Loading…"

After **35+ seconds** of waiting (across three reloads), the page stays on the auth splash:

> **JUNO** Financial dashboard
> Loading…

…and never advances. The sign-in form is never rendered. A user cannot sign up, sign in, or reset a password. No console errors except Chrome-extension noise. The "viewable for any user" check below — i.e. the very first thing a new viewer or investor would do with the link in MIGRATION.md step 1 — fails completely.

**Diagnosis from the network log:** every static asset and every esm.sh Supabase SDK chunk loads with HTTP 200 (32 requests captured). **Zero requests to `https://mbehvcfiakjznzqkymse.supabase.co` are ever initiated** — not the REST endpoint, not `/auth/v1/user`, not the realtime WebSocket, not the RPC `get_state_for_current_user`. The Supabase backend itself is alive (I separately hit `https://mbehvcfiakjznzqkymse.supabase.co/rest/v1/` and got the expected `{"message":"No API key found in request"}` response — Supabase project is up, REST gateway is healthy). So the dashboard client is hanging *before* its first auth call.

**Most likely root cause** in `public/state.js`, `bootstrap()`:

```js
export async function bootstrap() {
  state.sync.status = "loading";
  notify();                                  // notify #1, but auth.loading is still true
  try {
    const user = await getCurrentUser();
    if (user) { ... }
    state.auth.loading = false;              // <-- flag flipped, but NO notify here
    const remote = await fetchFinancialState();   // any hang here = forever splash
    if (remote?.state) { ... } else { state.sync.status = "idle"; }
  } catch (e) {
    console.warn("Bootstrap failed:", e);    // catch does NOT set auth.loading = false
    state.sync.status = "error";
    state.sync.last_error = e?.message || String(e);
  }
  await onAuthStateChange(...);              // another await before the next notify
  notify();                                  // notify #2 — finally
}
```

Two latent problems combine into one production bug:
1. **Missing `notify()` immediately after `state.auth.loading = false`** (state.js:147). Even if `getCurrentUser()` resolves to `null` promptly, the auth UI doesn't render until `fetchFinancialState()` AND `onAuthStateChange()` both complete.
2. **The `catch` block never resets `auth.loading`.** If `bootstrap()` throws partway through, the user is stuck on "Loading…" with no recovery path.
3. **No timeout / circuit-breaker.** If any await in the bootstrap chain hangs (RPC slow, WebSocket negotiating, esm.sh transient slowness), the user never sees a fallback.

This is C0 — it goes above C1 in priority because right now nobody can use the dashboard at all. Recommended patch (small, targeted, low risk):

```js
export async function bootstrap() {
  state.sync.status = "loading";
  notify();
  // Race the entire auth phase against a 6-second budget so the auth UI always shows up.
  const authPhase = (async () => {
    const user = await getCurrentUser();
    if (user) {
      state.auth.user = { id: user.id, email: user.email };
      state.auth.profile = await fetchMyProfile();
    }
  })();
  try {
    await Promise.race([
      authPhase,
      new Promise((_, rej) => setTimeout(() => rej(new Error("auth timeout")), 6000)),
    ]);
  } catch (e) {
    console.warn("Auth bootstrap timed out / failed:", e);
    state.sync.last_error = e?.message || String(e);
  } finally {
    state.auth.loading = false;
    notify();                                // <-- render the auth screen NOW
  }

  // Then load financial state best-effort (don't block the UI)
  try {
    const remote = await fetchFinancialState();
    if (remote?.state) {
      applyStateBlob(remote.state);
      state.sync.server_version = remote.version || 1;
      state.sync.status = "saved";
      writeLocalCache();
    } else {
      state.sync.status = "idle";
    }
  } catch (e) {
    state.sync.status = "error";
    state.sync.last_error = e?.message || String(e);
  }
  notify();

  // Auth state listener — fire and forget
  onAuthStateChange(async (event, session) => { ... }).catch(() => {});
}
```

Three changes: `notify()` right after `auth.loading = false`; a 6 s timeout on the auth phase so the UI always advances; financial-state load is no longer in the critical path for rendering the sign-in screen.

### What I could observe of the visual design (auth splash only)

The auth splash itself, while it lasts forever, is clean: a single card with `JUNO` in bold + `Financial dashboard` in muted weight, "Loading…" beneath, sitting on a near-white background (~#f5f5f5). At 1568 px viewport the card is horizontally centered (≈600 px wide, x≈585–985). Padding and rounded corners look fine.

What's missing or odd:
- **No favicon.** The browser tab shows the default Chrome doc icon. Trivial fix; nine times out of ten this is the thing that signals "professional product" to an external viewer.
- **No progress indicator besides static "Loading…" text.** A spinner or progress bar would at least communicate that the app is alive. With the bug above, the user has no way to distinguish "still loading" from "permanently dead."
- **No retry button or error fallback after N seconds.** Combined with the bug above, this is what makes the production state user-hostile.
- **No marketing/title-card content while loading.** Could carry a "We're forecasting your portfolio…" or just brand color while the app initializes. Minor.

### Console / network artifacts of note

- A Chrome extension (likely Acrobat / Adobe DC, id `efaidnbmnnnibpcajpcglclefindmkaj`) is injecting ~10 content scripts into the dashboard page. That's the user's environment, not yours, and the "asynchronous response channel closed" exceptions in the console are theirs, not the app's. Worth noting only because a user looking at DevTools in their own browser will see exception lines and think the dashboard is broken — when the actual bug (C0) is invisible (no console output).
- esm.sh dependency chain: the dashboard pulls the Supabase JS SDK plus seven sub-modules from esm.sh on every cold load (auth-js, functions-js, node-fetch, postgrest-js, realtime-js, storage-js, node/buffer, etc.). That's eight third-party cross-origin module fetches blocking the boot path. A single esm.sh hiccup makes the whole app slow. For a system that's supposed to be the system of record, bundling Supabase locally (or at minimum pinning to a single import) would remove a real availability dependency. Not urgent, but worth doing before the "retire the Excel" date.
