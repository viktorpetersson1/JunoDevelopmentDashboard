## 1. Summary

The application is now signed-in-usable, which is a real step up from yesterday's bricked load. Nav is responsive, charts render, the engine is computing, autosave is wired. But for a system that's about to retire the Excel as the system of record, three things make today's state unfit for that role: (a) **per-project IRR is broken to the point of comedy — Projects 7–11 each show an annualized IRR of 77,461,852,536.9% on the live Projects table**, which any user opens within seconds of signing in; (b) **the Sensitivity view hangs the renderer for 30+ seconds and never comes back** — I reproduced it twice, both times locking the tab; (c) **the per-project sensitivity table at the bottom of every Project Detail page shows "Build cost +10% → profit goes UP"**, because sale price is auto-derived from cost-plus-margin, so cost shocks self-correct in the model. That's not just a UX bug — it's a sensitivity table that gives the opposite of correct intuition on the single most-asked-about driver in development.

Beyond those, there are smaller-but-shippable issues: waterfall distribution tiers don't sum to the gross distribution shown above them (~$300k unallocated and silently absorbed by "n/a (self)"), the cash flow grid double-scrolls horizontally, the Annual P&L now silently shows an FY30 column that doesn't exist in the Excel benchmark, the footer still says "v1 prototype (read-only audit)" while we're at v10+, and the Settings panel still tells the user "All state is stored in your browser's localStorage" months after the Supabase migration.

**Do not retire the Excel until C1–C3 below are fixed.** They're the kind of thing a co-investor or lender will see in the first thirty seconds.

## 2. Critical issues

### C1. Per-project IRR shows 77,461,852,536.9% for Projects 7–11

Reproduced on the live Projects table, viewport 1568×750, scenario = Base case. Projects 6 and 7 are identical inputs except start date (Aug 27 vs Dec 27), but Project 6 shows IRR 57.7% and Project 7 shows IRR 77,461,852,536.9%. Same value for Projects 8, 9, 10, 11.

That's bisection overflow in `engine.js → monthlyIRR()`. The function:

```js
export function monthlyIRR(equityCashFlows, opts = {}) {
  const { maxIter = 200, tol = 1e-9, lo = -0.99, hi = 10 } = opts;
  ...
  for (let i = 0; i < maxIter; i++) {
    const mid = (a + b) / 2;
    const fm = npv(mid);
    if (Math.abs(fm) < tol || (b - a) < tol) return mid;
    if (fa * fm < 0) { b = mid; fb = fm; } else { a = mid; fa = fm; }
  }
  return (a + b) / 2;
}
```

The upper bracket `hi = 10` is a monthly rate of 1000%; annualized that's `(1+10)^12 - 1` = ~3.13e12, which when multiplied out and rounded gives roughly the 77e9 % displayed. For Projects 7–11, the equity cash flow series probably converges very slowly or has a near-pathological shape (small calls late in the horizon, a large terminal distribution), so the bisection terminates at or near the upper bracket without finding a meaningful root.

**Fix:**
- Cap `hi` at something sane like 1.0 (100% monthly is already absurd) and explicitly return `null` (or "n/a / out of range") when the rate hits the cap.
- Reject series that don't have at least one sign change *and* a meaningful cash-flow magnitude before computing IRR.
- In the UI, render `null` IRR as "—" rather than letting JS string-format a 13-digit number.
- Same fix is needed for `annualizedIRR(monthlyRate)` (engine.js:661) — clamp the input.

This single bug, visible on the second screen a new user opens, is the most damaging issue in the product right now.

### C2. The Sensitivity view hangs the renderer indefinitely

Clicked the Sensitivity nav button twice, in two different sessions. Both times the tab became completely unresponsive — `screenshot`, `get_page_text`, `navigate` all timed out for 30+ seconds. The second time I had to open a new tab to recover. The browser is not dead — the Sensitivity view's render is on the main thread and never yields.

I could not see the actual rendered Sensitivity page so I don't know which sub-component is the culprit. From the source (engine.js:564 `monteCarlo()` and ui.js's sensitivity renderer with the two-way heatmap), suspects:
- A two-way heatmap that runs `aggregatePortfolio()` once per cell (default 11×11 = 121 full portfolio recomputes — each is 10 projects × 49 months across the engine).
- A tornado that does 5×2 = 10 full portfolio recomputes plus chart instantiation.
- Auto-running 1000-trial Monte Carlo on render (would be 1000 × full-portfolio computes = catastrophic). I don't think the Sensitivity view does this — Risk does — but I couldn't verify because the page wouldn't render.

**Fix in priority order:**
1. Don't run any compute heavier than O(20 portfolio recomputes) on render. Either lazy-load the heatmap behind a button, downsample the grid to 5×5, or memoize per-axis values.
2. Move Monte Carlo and the two-way heatmap into a Web Worker. The engine is pure (no DOM, no window references) so this is a clean lift.
3. Add a render-time budget check: if the page hasn't yielded back to the event loop within ~500ms, surface a "Computing… ⏸ cancel" banner.

Right now this view is a foot-gun for the master admin and an "the app is broken" experience for any viewer who clicks it.

### C3. Per-project sensitivity table shows "Build cost up → profit up"

On Project Detail for 84 SBR (Project 2), the "Sensitivity (this project)" table reads:

| Case | Profit | Δ vs current |
|---|---:|---:|
| Build cost +10% | $1.0M | +$71k |
| Build cost -10% | $882k | ($71k) |
| Sale price +10% | $1.7M | +$791k |
| Sale price -10% | $161k | ($791k) |
| Interest +200bps | $894k | ($59k) |
| Interest -200bps | $1.0M | +$59k |
| Margin → 20% | $636k | … |

A residential developer reading this draws the obvious conclusion: build cost going up is fine, even *good* for profit. That is the opposite of reality. The cause is in `engine.js → calcProject()`:

```js
const totalCostPerSqft = totalCostExFinancing / project.villa_sqft;
...
} else {
  salePerSqft = totalCostPerSqft * (1 + eff.target_margin) * eff.sale_price_multiplier;
  salePrice = salePerSqft * project.villa_sqft;
}
```

When there's no `sale_price_override_usd`, sale price = cost × (1 + margin). Increase build cost → cost basis grows → sale price grows by 1 + margin × the cost increase. Net profit goes *up* in absolute terms because the margin operates on a larger base.

This is a defensible underwriting heuristic at the *very start* of a deal — but it's wrong as a sensitivity. A real cost shock cannot raise the price a buyer pays for a Hamptons villa. Once a project has a target sale price (which all 10 projects ostensibly do — see `_excel_sale_price` in `data.js`), build cost shocks eat directly into margin.

**Fix:**
1. **The sensitivity table should always run at a fixed sale price**, not at the cost-plus-margin pricing. Force-pin `salePrice` to whatever the current scenario produces, then perturb `build_cost_multiplier` and recompute *only* the cost side.
2. Default-populate `sale_price_override_usd` from `_excel_sale_price` on each project. The "Use Excel sale price" button is the right idea but it's manual today; the cost-plus default is misleading 90% of the time.
3. Add a banner explaining the pricing methodology on each project detail page: "Sale price is currently *derived* from cost × (1 + margin). To use a market-set price, click 'Use Excel sale price' above." Without this, every screenshot of the per-project sensitivity table is potentially defaming the model.

The portfolio-level tornado in Sensitivity has the same hazard (when I can finally see it).

### C5. No optimistic concurrency on `saveFinancialState`

The combination is unsafe for multi-user use.

## 3. Important but not urgent

### I1. Annual P&L silently shows an FY30 column that wasn't in the Excel

In calendar-FY mode the engine buckets Jan-2030 cash flows into FY30, producing a 5-year P&L. Excel has 4 FYs (FY26–FY29) because Juno's 13-month FY rolls Jan-2030 into FY29. The page title still says "Annual P&L roll-up — Source: matches Juno Forecast cols BA–BD (FY26–FY29)" but the table now shows 5 columns. The user has to know to toggle Fiscal Year mode in Settings to get back to the 4-column Excel layout.

This isn't wrong — the calendar mode is more conventional — but the **header claim of matching Excel BA-BD is now false** under the default mode. Either change the default to Juno-13, or update the panel subtitle to reflect the current mode.

Also: the FY30 column has $6.6M in sales and zero in everything except construction-related lines — it's a one-month stub. Showing it at full-column width makes the table feel like there's a real fifth fiscal year worth $6M of meaningful activity, which there isn't.

### I2. Waterfall distribution tiers don't reconcile to gross distribution

From the live "Distribution tiers" panel (signed in as Viktor, single sponsor investor):

```
1. ROC:           $7.8M
2. Pref to LP:    $2.8M
3A. GP catch-up:  n/a (self)
3B. To hurdle:    $0
4A. Above hurdle: $0
4B. Carry to GP:  n/a (self)
                  -----
Sum visible:      $10.6M
```

The "Gross distribution" KPI immediately above this table says $10.9M. The missing $0.3M was consumed by tier 3A (GP catch-up) but rendered as "n/a (self)" because the only investor is the sponsor — so the cash exists, it just isn't visible in the breakdown.

For a sole-sponsor case this is mathematically harmless, but the moment a non-sponsor LP appears the user is going to add the tier columns expecting them to sum to gross, and they won't unless the engine accounts for the catch-up explicitly. Render the catch-up as a real number even for self, or add a "Total distributed: $10.9M ✓" reconciliation row at the bottom.

### I3. The Cash Flow grid has double horizontal scrollbars

Two horizontal scroll thumbs visible at the bottom of the Cash Flow screen — one for the table's `.scroll-x` wrapper, one at the window level. The window-level scrollbar means the page itself overflows. Some block in the cashflow renderer is wider than the viewport (or has a `min-width` it shouldn't). Add `overflow-x: hidden` to the page container or fix the offending block's width.

This is a small thing visually but it makes the page feel buggy. Easy fix.

### I4. Waterfall "Equity timeline" chart has Y-axis up to $35M for ~$15M of actual data

Cumulative deployed peaks at ~$10M, returned at ~$15M, but the Y-axis runs to $35M. Two-thirds of the panel is whitespace. Either set `suggestedMax` to `max(data) * 1.2` or let Chart.js auto-scale (it's clearly being overridden somewhere).

### I5. Status (legacy) shows "SOURCING" everywhere, ignoring committed/pipeline

On the Projects table, every row shows the SOURCING stage badge. Project 2 (committed in the seed data) and Project 4 (committed) both show SOURCING. This is the dual-field problem from yesterday's I6 made visible: `stage` has overwritten what the lifecycle should say, and the badge function only consults `stage`. The legacy `status` field is still set to `committed`/`pipeline` per the form on Project Detail but isn't being shown in the badge column.

Pick one. The Project Detail form still has both a "Status" dropdown (pipeline/committed/in-build/sold) and a separate "Stage" dropdown. They get out of sync trivially.

### I6. "Pref cleared / hurdle cleared" status is incomplete

The Waterfall by-investor table shows a single status badge: "PREF CLEARED". That's correct for KPC at 10.7% > 8% pref. But hurdle is 20% and IRR is 10.7%, so hurdle is *not* cleared. A user glancing at this and seeing a green "PREF CLEARED" badge thinks everything is fine. Show both: "Pref ✓ / Hurdle ✗" or "Cleared pref, below hurdle by ~9.3 pts."

At 1568px the Portfolio shows 8 KPI cards in the first row plus "Simple payback" wrapping alone to row 2 with 7 empty columns. Either fit 8 into a 2×4 grid (4 columns × 2 rows) or 9 into a 3×3, or drop a KPI you don't need. The current layout looks accidental.

Per C2 above, I can't see the actual page. But the same `aggregatePortfolio()` runs underneath, and the same cost-plus pricing applies at portfolio level. ### I10. Footer source date `snapshot 2026-05-10` is hard-coded

Footer reads `Source: Juno_Cash flow Forecast_20260412_MASTER.xlsx · snapshot 2026-05-10`. This is hard-coded in `ui.js:2779`. `if (confirm("Sign out?")) await signOut();` in ui.js:230. Two small problems: (a) confirm() dialogs are jarring on a polished web app — use an inline confirmation or just sign out, since accidental sign-outs are easily recoverable; (b) headless tooling (and some accessibility tools) get stuck on these. Replace with an inline disclosure.

## 4. Suggestions

Ranked.

### S1. Default every project's `sale_price_override_usd` to its `_excel_sale_price` on first load

Today `_excel_sale_price` is an annotation, not a real override, and the cost-plus-margin pricing produces visibly wrong sensitivity intuition (see C3). At least for the 10 seed projects, the Excel sale price is a defensible market-set figure. Auto-populate `sale_price_override_usd` from `_excel_sale_price` on baseline load, and let users clear it back to cost-plus if they're underwriting a brand-new deal. This single line of seed-data work fixes C3's worst expression.

### S2. Cash-on-cash, profit margin %, and contingency burn as named KPIs

Repeating from yesterday's S1. None of these are on the Portfolio view today. The closest is "Effective margin" (which is profit/sales = effectively profit margin) and "Yield on cost" (which is profit / all-in-cost). Add cash-on-cash explicitly (annualized equity distributions / equity in), and add the contingency concept (global `contingency_pct`, per-project `contingency_used`).

### S3. Add a portfolio-level schedule-variance KPI

Each project has `start_date`. There's no equivalent `actual_start_date` field, but adding it is one schema line. Then surface `Σ |actual_start - forecast_start|` weighted by sqft as "schedule slip exposure" on Portfolio. This is exactly the metric a residential developer wants to brief a lender on but doesn't easily see anywhere today.

### S4. Move the heavy compute (Monte Carlo, two-way heatmap, tornado) into a Web Worker

The engine modules are pure ES modules with no DOM dependency — they're trivially worker-portable. Right now Sensitivity locks up the tab (C2) and Risk's Monte Carlo will too if a user clicks "Run simulation" with 1000 trials × full portfolio. A worker fixes both with a one-time refactor.

### S5. Build a "Sources of variance vs Excel" page

The reconciliation work in PHASE_4_VALIDATION is genuinely impressive engineering, but it's invisible to anyone not reading the docs. A panel under Settings showing "Match Excel mode is off → expect +$5.4M build cost vs Excel (under-allocation), −$1.4M sales vs Excel (pricing methodology), +0.1M financing vs Excel" would dramatically increase trust the first time someone runs both side by side. Today the "Match Excel mode" button is a black box.

## 7. UX from the exec team's seat

This section is written from the perspective of the people who'd actually use this tool day to day — the master admin, a CFO, the operating partner, and a co-investor. Not a developer, not a financial-modeling specialist. Someone running ten sequential Hamptons villa projects over four years who already has Excel and is being asked to switch.

The question I'm answering is: **does this dashboard, as it stands today, make this team's job easier than the Excel does?** And the answer right now is: for the modeling and forecasting layer, yes. For the operating layer, no, because the operating layer doesn't exist yet.

### 7.1 What works

Genuinely. Don't dismiss these.

- **Portfolio overview as a one-screen "is anything red?" check.** The KPI row + alert banner + monthly stacked chart + annual P&L is a defensible morning-coffee view. A managing partner can scan it in ten seconds.
- **Pipeline gantt is intuitive.** Anyone who has ever run a Microsoft Project or a Smartsheet will immediately grasp what they're looking at.
- **Project Detail has the right shape.** KPIs at top, inputs on the left, sensitivity on the right, monthly chart below. That's the page a project manager would expect.
- **Scenario presets ("Stress", "Optimistic") and named scenario save/load** are the single biggest workflow win over Excel. In Excel you make a copy of the workbook, name it `…_Stress.xlsx`, and pray. Here you click two buttons. This is *the* product moat — lean into it.
- **CSV exports** mean the CFO still gets data into their existing pivot tables. Don't underestimate how much friction this removes.
- **The activity-log concept** is a real audit gain over Excel, even if the implementation has issues (I7, I4-yesterday).

### 7.2 What feels broken on first impression

This is the bit that loses the room in the first five minutes of an investor demo:

- **The IRR column on Projects.** Six of the ten rows show `77,461,852,536.9%`. The first instinct of any reader is "the model is broken." Even if the rest of the dashboard is flawless, that one column ends the conversation. (C1.)
- **Every project shows the same stage badge: SOURCING.** A villa-development exec looking at this immediately asks: "Why does it say all ten projects are in sourcing? Project 2 is in design, we're meeting the architect Tuesday. What is this tool actually tracking?" (I5.) The dashboard is showing them a *modeling object* labeled "stage", not the real-world state of the project. There is no concept in the data model of *where the project actually is right now*.
- **"Build cost +10% → profit +$71k" on every Project Detail sensitivity table.** A villa dev reads this and thinks one of two things: "this is wrong" (correct), or "huh, maybe I should let costs run" (catastrophically wrong). Either way they stop trusting the sensitivity numbers. (C3.)
- **Click Sensitivity, browser dies.** Anyone exploring the nav will hit this within a minute, and there is no "loading" or "computing" indicator — the browser just freezes. (C2.)
- **Footer says "v1 prototype (read-only audit)".** While the rest of the screen is selling them a finished product. Confidence drops. (I7.)

These five things are 95% of why the exec team would not yet recommend this to their LPs as the investor portal. None of them are deep architecture; all five are fixable inside a week.

### 7.3 Information architecture: the dashboard answers the wrong question

The dashboard is structured around *the financial model* — Portfolio, Projects, Cash Flow, Waterfall, Scenario, Sensitivity, Risk. Those are great categories for a financial analyst.

An exec team running ten villas does not think in those categories. They think in:

1. **"How are we doing this month?"** — actuals vs plan, cash position, what's already happened. Today there is no "this month" view. Everything is forward-looking modeling.
2. **"What do I need to do this week?"** — pending approvals, decisions, capital calls, hand-offs. Today there is no task / decision queue.
3. **"What's the state of each project?"** — not the financial KPIs of each project, the *operational* state. Permits filed? GC selected? Foundation poured? Listed? Today the projects list shows Margin / MOIC / IRR / YOC — finance KPIs, not operational status.
4. **"Where are the surprises?"** — variance vs plan, both schedule and cost. The Budget vs Actual table exists per project but is collapsed inside a `<details>` disclosure on Project Detail. Should be on the Portfolio overview.

The dashboard treats the financial-model view as the home page. A villa-development exec wants the operational-status view as the home page, with the financial model as a tab they click into when they need it.

**Concrete fix**: rename "Portfolio" to "Pipeline" or "Operations", and put a status-by-project board there — stage, days in stage, next milestone, owner, blockers — with the current Portfolio overview becoming a "Financials" tab next to it.

### 7.4 The "where are we today vs what are we forecasting" problem

This is the deepest information-architecture issue and it deserves its own subsection.

Every KPI on the dashboard is currently a *forecast over the model horizon*. Peak equity $7.8M (over the next 49 months). Max debt $11.7M (over the next 49 months). Profit $6.5M (over the next 49 months). Annualized IRR 10.7% (over the next 49 months).

An exec sees "Peak equity required $7.8M" and they're not asking "what's the peak across the 49-month forecast"; they're asking one of:

- "How much equity have we *actually* deployed so far?"
- "How much do we have committed but undrawn?"
- "How much will we need next month?"
- "How much will we need in the worst case before any sales close?"

The dashboard does not distinguish between these. There is no "actual to date" overlay on the chart, no "committed vs drawn vs called" breakdown, no "next 30/60/90 days projected need." The Cumulative debt vs equity chart at the bottom of Portfolio shows balances over the full horizon, but there's no vertical "today" line on it.

**This is the single biggest gap between "financial model with a login" and "system of record for an operating company."** The Excel had the same problem; that's not a defense, that's the point — the dashboard hasn't yet solved what the Excel was bad at.

**Concrete fix**: add a "today" anchor in the engine. Every chart gets a vertical line at the current month. Every monetary KPI gets an "as of today / forecast EOY / forecast horizon-end" toggle. The Portfolio page leads with current state, not horizon totals.

### 7.5 Missing concepts that an operating villa-dev shop will need within 90 days of using this

Roughly in priority order, the things a CEO of a residential developer will ask for and won't find:

1. **Decision queue / pending approvals.** "Things you need to sign off on this week." Today: there is nowhere for the operating partner to flag "Need GMP signature on Project 4 by Friday." Suggestions queue exists for LLM-generated changes but not for human-originated decisions.
2. **Capital call calendar.** "On Mar 15 you need $1.2M from LPs for the Project 2 land close." The cash flow grid has the data but isn't surfaced as a discrete action item.
3. **Permit / inspection tracker.** Per project: zoning approved? Building permit filed? Issued? Final inspection? CO issued? None of this exists.
4. **Change orders.** A construction project has 10-30 of these. None exist in the data model. This is the difference between a forecast and a reality.
5. **RFI / submittal log.** Same.
6. **Marketing & sales activity.** When a villa lists, the exec wants: days on market, # of showings, # of offers, list price vs comp price, price reductions. Fields exist for listing_date/closing_date but no log of showings or offers.
7. **Vendor / contractor directory.** Architect, GC, structural engineer, landscape, attorney, listing agent — each with project assignments, contracts, payment terms. Today: zero.
8. **Investor capital account statement.** Each LP wants a statement: capital committed, capital called, capital returned, current capital account balance, projected distributions. The waterfall page is a model output, not a statement. There's a difference.
9. **Document repository.** Land DD documents, surveys, permits, contracts, inspection reports, CO. Today: zero. This is where Box / Dropbox actually wins versus this tool.
10. **Property tax + insurance tracking during hold.** Carrying costs are not modeled per project, only as flat OPEX. For a four-year horizon with 10 sequential projects, this matters.
11. **GMP / hard-cost contract amount captured separately from `build_cost_per_sqft`.** Today the build budget is a $/sqft assumption. After a GC is signed, the real number is a contract amount. The dashboard should show both and the variance between them.
12. **Contingency budget.** Standard 5–10% on hard costs in residential construction. Not modeled at all.

You don't need all 12 in v1. But you cannot retire the Excel until items 1, 2, 3, 4, 6, and 8 exist somewhere — because those are the things the Excel didn't cover either, and the team is currently doing them in their head or in a Notion doc. The dashboard is positioned to absorb those workflows; it just hasn't yet.

### 7.6 Investor-facing concerns

KPC is currently a sole sponsor — `data.js` has one investor (`kpc`, share 100%, role sponsor). The waterfall page works in this case but mostly says "n/a (self)" because there's no LP to distribute the carry to.

Two implications for what an exec will see when they bring in actual LPs:

- **The Waterfall view will become genuinely important.** Right now it's a financial-modeler's plaything. The moment LP 1 invests, this becomes the investor-facing screen. **Plan now for**: a per-LP login that defaults to *their* waterfall row only, with no portfolio-wide KPIs visible. The current viewer/viewer_basic role split is too coarse — an LP needs their *own* data, not a redacted version of everyone else's.
- **The "investor distribution statement" pdf/printable** doesn't exist. The "Export printable HTML report" generates a portfolio summary, not a per-investor statement. The first time KPC distributes to an LP, that LP will ask for "my K-1 and my capital account statement." The dashboard should produce both at one click.

This is the kind of thing where you lose institutional LPs in the diligence phase if you can't show it. Family-office LPs forgive a lot; institutional LPs do not.

### 7.7 Things that look polished but read wrong

These are smaller and easier to fix than 7.5, but they shape first impressions:

- **The role badge "SUPER ADMIN" rendered in uppercase pill** looks like it was copied from a B2B SaaS template. For an internal villa-dev tool, this is overcorporate. "Owner" or "Managing partner" reads more naturally for the master admin role.
- **The "Ask Juno" floating button** has a sparkle icon. Reasonable visual. But the *label* — "Ask Juno" — refers to the brand of the dashboard, which is also called Juno. A user can't tell if this is asking Juno-the-brand a question, or asking an "AI assistant" that happens to be called Juno. Renaming to "Ask AI" or "Ask the assistant" removes the recursion.
- **"Scenario: Base case" in the topbar** is the only scenario indicator. If you save and load a named scenario, the rest of the topbar doesn't change. The numbers on the Portfolio page will silently be different. An exec who scenario-shifts on Tuesday afternoon and looks at the dashboard on Wednesday morning may not realize they're looking at the stress case. Make the topbar background tint when the scenario != Base.
- **The "Risk" page is named for the act, not the artifact.** A CFO looking at the nav reads "Risk" and thinks "compliance risk register" or "operational risk." This is actually a Monte Carlo stress test. Call it "Stress test" or "Monte Carlo" in the nav.
- **The "Suggestions" view is empty for everyone who hasn't used the LLM** and offers no other concept of human-originated suggestions or decisions. As the master admin I want a queue of "decisions to make" that I can populate myself, not just LLM-proposed patches. The current implementation is single-purpose and will look unused for months until someone discovers Ask Juno → Suggest mode.
- **The Activity log talks like a software dev tool.** "Category: global, message: interest_rate_apr changed, detail: { key: ..., prev: 0.095, next: 0.10 }." A non-technical user would prefer "Viktor changed the interest rate from 9.5% to 10.0%."
- **"Match Excel mode" as a button** is confusing. It implies a special mode, but really it's "reconcile the dashboard to the Excel by tweaking three settings." Better: a "Reconciliation snapshot" section that shows side-by-side dashboard vs Excel with each delta explained, and a one-click "Apply Excel-matching assumptions" inside that section.

### 7.8 The mobile/phone question

I did not test mobile breakpoints (per §5). But for an exec team, mobile use is not optional — partners check positions in airport lounges and between meetings.

The topbar today has 13 nav buttons spread across the full width at 1568px. Below ~1100px those will wrap. Below ~700px (phone), they'll be unusable as a horizontal nav.

A serious mobile experience for this product would be:
- A bottom-tab nav with 4 items max: **Today / Projects / Money / More**.
- "Today" = the operational status view I described in §7.3.
- "Projects" = current Projects list, vertical card layout instead of wide table.
- "Money" = current Portfolio + Cash flow + Waterfall.
- "More" = everything else behind a drawer.
- KPI cards stack to 1- or 2-column vertically.
- Charts are interactive (Chart.js supports pinch-zoom but it has to be enabled).

This is a separate phase of work, but worth scoping now because it influences component decisions you're making for desktop today.

### 7.9 One-screen summary of what to do

If I were briefing the exec team on what changes between now and "we can retire the Excel" — and treating C1–C5 as table stakes — the top of the operational backlog should be:

1. **Add an "as-of-today" overlay** to every chart and every monetary KPI. Status quo (forecast over horizon) is the wrong default. (§7.4)
2. **Add a Today / Operations home page** that leads with operational status, capital calls upcoming, decisions pending, and budget-vs-actual exposure. Move Portfolio to a Financials tab. (§7.3)
3. **Replace the SOURCING-everywhere lifecycle problem** by collapsing `status` and `stage` into one field, and by surfacing "days in current stage" so the exec sees movement. (§7.2, I5)
4. **Build a capital call calendar and a decision queue** (§7.5 items 1 and 2). Both are mostly UI on existing data.
5. **Build a per-LP statement view** before bringing in any actual LP. (§7.6)
6. **Rename / soften** the dev-tool language (Risk → Stress Test, Activity → History, Suggestions → Approval queue, super_admin badge → Owner).
7. **Mobile** — not v1, but scope it now.

None of those is a new financial concept. They're all UX and information-architecture work. The hard analytical layer is already there.
